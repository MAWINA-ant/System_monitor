# System_monitor

![CI](https://github.com/MAWINA-ant/System_monitor/actions/workflows/ci.yaml/badge.svg)
[![Go Report Card](https://goreportcard.com/badge/github.com/MAWINA-ant/System_monitor)](https://goreportcard.com/report/github.com/MAWINA-ant/System_monitor)

Демон системного мониторинга. Он собирает информацию о системе, на которой запущен, и по gRPC отдаёт её клиентам
потоком снимков (server-side streaming). В комплекте простой клиент, который выводит статистику в виде таблиц.

Финальный проект курса OTUS Golang Professional.

## Что собирается

| Подсистема | Что отдаёт | Источник (Linux) | Усреднение за окно M |
|---|---|---|---|
| Load average | load за 1, 5 и 15 минут | `/proc/loadavg` | нет, среднее считает ядро |
| CPU | `user`, `system`, `idle` в процентах | `/proc/stat` | да |
| Загрузка дисков | tps и KB/s по каждому диску | `/proc/diskstats` | да |
| Использование дисков | занято МБ и %, занято inode и % по каждой файловой системе | `/proc/mounts` и `statfs` | нет, мгновенное значение |
| Сеть | слушающие TCP/UDP сокеты (команда, PID, пользователь, протокол, порт), число TCP-соединений по состояниям | `/proc/net/*`, `/proc/<pid>/fd` | нет, мгновенное значение |

Не реализовано: top talkers по сети (см. [Ограничения](#ограничения)).

Вся логика сбора написана только на стандартной библиотеке Go. Сторонние библиотеки используются лишь для транспорта
(gRPC и protobuf).

## Как устроено расписание

Клиент в запросе указывает два числа: **N**, как часто присылать снимок, и **M**, за какое последнее время усреднять.
Например, при `N=5`, `M=15` демон молчит первые 15 секунд, затем присылает снимок за 0-15 с, в 20-й секунде снимок
за 5-20 с, в 25-й за 10-25 с и так далее.

Для каждого клиента сервер создаёт собственные сборщики и фоновые сэмплеры, поэтому у каждого клиента своё `M`.
Когда клиент отключается, сэмплеры останавливаются. `N` и `M` должны быть в диапазоне от 1 до 3600 секунд.

## Быстрый старт

Нужны Linux, Go 1.27.1 (версия указана в `go.mod`) и `make`.

```bash
make build
./bin/server -port 8080
```

В другом терминале:

```bash
./bin/client -addr localhost:8080 -n 5 -m 15
```

Пример вывода клиента (`-n 1 -m 2 -sections load,cpu,diskload`):

```
=== 2026-10-04 21:44:28 ===
Load average: 1.72 1.34 0.73 (1/5/15 min)
CPU: user 2.9%  system 0.7%  idle 96.4%

Disk load
DEVICE    TPS  KB/S
nvme0n1  0.00  0.00
sda      0.00  0.00
```

### Флаги сервера

| Флаг | По умолчанию | Описание |
|---|---|---|
| `-port` | `8080` | порт gRPC-сервера |
| `-config` | пусто | путь к JSON-конфигу с включёнными подсистемами (если пусто, включено всё) |

### Флаги клиента

| Флаг | По умолчанию | Описание |
|---|---|---|
| `-addr` | `localhost:8080` | адрес сервера |
| `-n` | `5` | присылать снимок каждые n секунд |
| `-m` | `15` | усреднять за последние m секунд |
| `-sections` | `all` | что печатать, через запятую: `load`, `cpu`, `diskload`, `diskusage`, `toptalkers`, `netstats` или `all` |

Если подсистема выключена на сервере, клиент пишет `disabled on the server`. Если данных нет, пишет `no data`.

## Конфигурация

Какие подсистемы собирать, задаётся JSON-файлом (`-config`). Пример лежит в [configs/config.json](configs/config.json):

```json
{
  "subsystems": {
    "loadAverage": true,
    "cpu": true,
    "diskLoad": true,
    "diskUsage": true,
    "networkStats": true
  }
}
```

- Ключи, которых нет в файле, остаются включёнными. Чтобы выключить подсистему, достаточно указать её со значением `false`.
- Неизвестный ключ считается ошибкой, это защищает от опечаток.
- Пустой файл или пустой `-config` означают «всё включено».
- Формат JSON выбран потому, что в стандартной библиотеке Go нет парсера YAML.

## Docker

```bash
make build-img                          # собрать образ system-monitor
make run-img                            # собрать и запустить на порту 8080
```

Или вручную:

```bash
docker run --rm -p 8080:8080 system-monitor
docker run --rm -p 8080:8080 \
  -v "$PWD/configs/config.json:/etc/system-monitor/config.json:ro" system-monitor
docker run --rm -p 9000:9000 system-monitor -port 9000
```

Образ собирается в два этапа (итоговый размер около 28 МБ), сервер внутри работает от непривилегированного
пользователя `app`.

## gRPC API

Контракт описан в [api/system_monitor.proto](api/system_monitor.proto):

```proto
service StatsService {
  rpc GetStats(StatsRequest) returns (stream Snapshot);
}
```

- `StatsRequest` содержит `n_seconds` и `m_seconds`.
- `Snapshot` содержит время снимка и по одной секции на каждую подсистему. Выключенная подсистема в сообщении отсутствует.
- Невалидные `n_seconds` и `m_seconds` дают ошибку `InvalidArgument`.
- Ошибка сбора данных завершает поток статусом `Internal`, клиент может переподключиться.

Сгенерированный код лежит в `api/statspb`. Пересоздать его можно командой `make generate` (нужны `protoc` и `sudo apt`).

## Разработка

| Команда | Что делает |
|---|---|
| `make build` | собирает `bin/server` и `bin/client` |
| `make run` | запускает сервер через `go run` |
| `make test` | юнит-тесты: `go test -race -count 100 ./...` |
| `make test-integration` | интеграционные тесты (с тегом `integration`) |
| `make lint` | `golangci-lint` v2.14.0 |
| `make build-img`, `make run-img` | сборка и запуск Docker-образа |
| `make generate` | генерация кода из `.proto` |

Интеграционные тесты поднимают настоящий gRPC-сервер с настоящими сборщиками, подключаются к нему клиентом и
проверяют, что поток приходит по расписанию, что открытый в тесте сокет появляется в снимке, что установленные
соединения попадают в счётчик, что отключённые подсистемы пропадают, а отмена клиентом останавливает работу сервера.
Они вынесены под тег `integration`, потому что каждый тест идёт несколько секунд реального времени.

CI (GitHub Actions, [ci.yaml](.github/workflows/ci.yaml)) на каждый push запускает пять job: `lint`, `test`,
`build`, `docker` и `integration`.

### Конфигурация линтера

`.golangci.yaml` основан на конфиге курса, но переведён в формат golangci-lint v2 командой `golangci-lint migrate`:
конфиг курса включает линтеры `deadcode`, `structcheck`, `varcheck`, `ifshort`, которые в новых версиях полностью
отключены (их заменил `unused`), поэтому старый файл не запускается. Дополнительно добавлены правила `depguard`
(разрешены стандартная библиотека, пакеты проекта, gRPC и protobuf) и тег сборки `integration`, чтобы линтер видел
интеграционные тесты.

## Ограничения

- **Только Linux.** Сборщики написаны под `/proc` и помечены тегом `linux`. Поддержки других ОС пока нет.
- **Top talkers не реализован.** Для него нужен захват пакетов (raw-сокет `AF_PACKET`, права root или `CAP_NET_RAW`).
  В конфиге такого ключа нет, клиент показывает эту секцию как `disabled on the server`.
- **PID и команда слушающего сокета** видны только для процессов, к которым у пользователя есть доступ. Чтобы видеть
  все, сервер нужно запускать от root. Для остальных в таблице стоит `-`.
- **Использование дисков** перечисляет все смонтированные файловые системы с ненулевым размером, как `df`, включая
  loop-устройства snap (они всегда заполнены на 100%). Список можно скрыть флагом `-sections`.
- **В контейнере** `/proc/loadavg`, `/proc/stat` и `/proc/diskstats` показывают данные хоста, а сеть и список
  файловых систем свои. С флагом `--network host` контейнер видит сокеты хоста, но пользователи показываются
  числовым uid, а PID и команда пустые.
- **Ошибка сбора данных** завершает поток клиента целиком (статус `Internal`), частичных снимков нет.
